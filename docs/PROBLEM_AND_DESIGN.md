## Part 1 - Problem Decomposition

### 1.1 The Raw Problem Statement (As Given)

Small Kenyan retailers coordinate deliveries over WhatsApp and phone calls. There is no record of who is assigned, no status visibility, and no proof of delivery.

### 1.2 What This Actually Means, Stripped of Narrative

Strip the story away and the underlying problem is a **coordination and visibility gap**, not a technology gap. Three distinct failures are happening simultaneously in the current (WhatsApp/phone) process:

| Failure                                         | Consequence                                                         |
| ----------------------------------------------- | ------------------------------------------------------------------- |
| No structured record of a delivery request      | Requests get lost, forgotten, or duplicated                         |
| No visibility into who is responsible right now | Retailer can't answer "where is my delivery" without calling around |
| No proof the delivery actually happened         | Disputes over "it was never delivered" have no evidence             |

**Reframed problem statement:** _Build a system that gives every delivery a single, trackable lifecycle, from request to confirmed delivery, with a clear owner at every stage, and a permanent record of what happened._

This reframing matters because it tells us the **system's core responsibility isn't "an app," it's a state machine with an audit trail.** Everything else (UI, endpoints, database) exists to serve that.

### 1.3 Actors (Personas), Restated as Roles With Responsibilities

| Actor              | Responsibility in the System               | What They Need to See                 |
| ------------------ | ------------------------------------------ | ------------------------------------- |
| **Retailer Staff** | Originates a delivery request              | Their own requests and current status |
| **Dispatcher**     | Allocates responsibility (assigns a rider) | All open, unassigned requests         |
| **Rider**          | Executes the delivery, reports progress    | Only their own assigned deliveries    |

Notice: each actor's need is scoped narrowly. This is a strong hint for **access boundaries** later (a rider should not see other riders' deliveries), even if full authentication is out of scope for this sprint.

### 1.4 Explicit Functional Requirements (Extracted, Not Assumed)

1. A retailer staff member can log a new delivery request (customer name, phone, address, item description).
2. A dispatcher can view all open requests and assign one to a specific rider.
3. A rider can view their assigned deliveries and advance the status (Assigned → Picked Up → Delivered).
4. The retailer can view the current status of any of their requests at any time.
5. Delivery completion must be **confirmed**, not just claimed, the brief specifies "scanning for order confirmation," implying a verifiable step, not a self-reported button press alone.
6. The system must support "syncing to get real-time requests", interpreted here as: dispatchers and riders need reasonably fresh visibility into new/updated requests without manual refresh-and-ask.

### 1.5 What's Explicitly NOT Specified (And Must Be Decided, Not Assumed)

- Is this single-retailer or multi-retailer? _(Decision needed - see Part 3)_
- Does a dispatcher belong to one retailer or serve many? _(Decision needed)_
- Is rider assignment manual (dispatcher picks) or automatic (system picks nearest/next-available)? _(Decision needed - brief says "a dispatcher assigns," implying manual)_
- What does "scanning" scan, a QR code generated by the system, or something external? _(Decision needed)_

Naming these explicitly, rather than silently picking defaults, is itself part of the deliverable, this is exactly the kind of thing a panel will ask "why this and not the alternative."

## Part 2 - Object-Oriented Domain Analysis

### 2.1 Noun Extraction (Candidate Classes)

Standard OOD technique: pull every noun from the requirements and the personas, then filter down to real domain objects (not attributes, not verbs, not UI concepts).

From the requirements: _retailer, staff, dispatcher, rider, delivery request, customer, phone, address, item description, status, assignment, confirmation, scan._

**Filtered candidate classes:**

- `Retailer` - a business account using the system
- `User` - a person acting in one of three roles (staff, dispatcher, rider)
- `DeliveryRequest` - the central domain object
- `StatusEvent` - a record of a state change (this isn't in the raw noun list explicitly, but it's _implied_ by "status visibility" and "proof of delivery," a senior engineer adds this because the requirement demands history, not just current state)
- `Confirmation` - the verification artifact tied to a completed delivery

Rejected as classes (these are attributes or values, not objects with independent identity/behavior): `customer name`, `phone`, `address`, `item description` - these are properties of `DeliveryRequest`, not domain objects in their own right, a customer here is not a system actor, just descriptive data.

### 2.2 Responsibility Assignment (CRC-Style)

For each class: what does it know, and what does it do?

**`DeliveryRequest`**

- _Knows:_ customer details, current status, who created it, who it's assigned to, when each transition happened (via its `StatusEvent`s)
- _Does:_ validates its own state transitions (cannot go from `Requested` directly to `Delivered`, must pass through `Assigned` and `Picked Up`), refuses invalid transitions
- _Collaborates with:_ `User` (creator, assigned rider), `StatusEvent` (its own history)

**`User`**

- _Knows:_ their role, which retailer they belong to (if applicable)
- _Does:_ performs role-specific actions, a `Rider` can advance status only on requests assigned to them; a `Dispatcher` can assign only unassigned requests; `Retailer Staff` can create requests and view their own
- _Collaborates with:_ `DeliveryRequest`

**`StatusEvent`**

- _Knows:_ which request it belongs to, what the status became, who caused it, when
- _Does:_ nothing beyond existing as an immutable record, this is intentionally a "dumb" object, its value is in being a permanent log, not in behavior

**`Confirmation`**

- _Knows:_ the code/token generated for a specific request, whether it's been validated
- _Does:_ validates a scan attempt against the expected code

### 2.3 Why Model It This Way - The Key OOD Decision

The most important design decision in this whole system: **`DeliveryRequest` owns its own state machine.** It is responsible for enforcing that `Requested → Assigned → Picked Up → Delivered` happens in order, and that a `Rider` cannot mark something `Delivered` without a valid `Confirmation`. This responsibility should NOT leak into the API route layer or the frontend, if either of those tried to independently decide "is this transition allowed," you'd end up with the validation logic duplicated and drifting out of sync, exactly the kind of fragility a panel will probe for under the "edge cases" question category.

This single decision, **keep the state machine's rules inside the domain object, not scattered across layers**, is worth being able to explain confidently and by name in the defense, it's a direct, concrete answer to "why did you design it this way."

### 2.4 Relationships Between Classes

```
Retailer "1" ────── "many" User (role: retailer_staff)
Retailer "1" ────── "many" DeliveryRequest (created by its staff)

User (rider) "1" ────── "many" DeliveryRequest (assigned to)

DeliveryRequest "1" ────── "many" StatusEvent (its history)

DeliveryRequest "1" ────── "0..1" Confirmation (only exists once picked up)
```

### 2.5 The State Machine (Formalized)

```
        create()
           │
           ▼
      [Requested] ──assign(rider)──▶ [Assigned] ──pickUp()──▶ [Picked Up] ──confirmDelivery(code)──▶ [Delivered]
           │                              │                        │
           └── (no skipping states) ──────┴────────────────────────┘
```

Invalid transitions (e.g., `Requested → Delivered` directly, or `Picked Up → Assigned` backward) must be explicitly rejected, not just "not built," this distinction matters: a panel asking "what happens if someone tries to skip a state" should get "it's rejected, here's the guard" not "we didn't think about that."

## Part 3 - Decisions on the Open Questions (Part 1.5)

Now that the domain model exists, resolve the earlier open questions deliberately:

| Question                         | Decision                                                                                                                             | Reasoning                                                                                                                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Single or multi-retailer?        | **Multi-retailer**                                                                                                                   | The brief's framing ("small Kenyan retailers," plural) implies a platform, not a bespoke single-shop tool. Costs little extra (`retailer_id` on `User` and `DeliveryRequest`) and is more defensible as a realistic product       |
| Dispatcher scope                 | **Per-retailer** for this sprint                                                                                                     | Keeps assignment logic simple (a dispatcher only sees and assigns within their own retailer's requests), avoids building cross-retailer routing logic under time pressure. Named explicitly as a scope decision, not an oversight |
| Assignment: manual or automatic? | **Manual**                                                                                                                           | Brief explicitly says "a dispatcher assigns it to a rider." Automatic assignment (nearest rider, load balancing) is a real future improvement, named in the roadmap, not attempted now                                            |
| What does "scanning" scan?       | **A system-generated confirmation code**, displayed as text/QR at Picked Up, entered/scanned by the rider (or retailer) at Delivered | No external hardware/service dependency, fully within a 4-day build, and mirrors a pattern already proven working in the Meridian Pivot check-in kiosk (`print_job_id` correlation)                                               |

## Part 4 - From Domain Model to Architecture

### 4.1 Layering (Where Each Responsibility Lives in Code)

```
Routes (FastAPI)
   ↓  - thin, no business logic
Services (domain logic lives here)
   ↓  - enforces the state machine, calls persistence
Persistence (raw SQL / asyncpg)
   ↓
PostgreSQL
```

The `DeliveryRequest` state machine rules (Part 2.3) belong in the **Services** layer, not in routes, not in raw SQL constraints alone (though a DB-level CHECK constraint as a second safety net is good practice, matching your own "design for failure early" principle).

### 4.2 High-Level Component Diagram

```
Retailer Staff UI ──▶ POST /requests ──▶ RequestService ──▶ DB
Dispatcher UI     ──▶ POST /requests/{id}/assign ──▶ RequestService ──▶ DB
Rider UI          ──▶ POST /requests/{id}/status ──▶ RequestService ──▶ DB
Any UI            ──▶ GET /requests/{id} (poll for sync) ──▶ RequestService ──▶ DB
```

### 4.3 "Real-Time Sync" - Resolved

Given the 4-day constraint, **polling** (client re-fetches every N seconds) is the honest, deliverable choice over WebSockets/push. This is a trade-off to name explicitly in the defense: _"We chose polling over WebSockets because it's simpler to implement correctly and test under our timeline; the cost is slightly delayed visibility (a few seconds), which is acceptable for a delivery status use case where sub-second updates aren't the actual user need."_
